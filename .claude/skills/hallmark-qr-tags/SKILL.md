# HUID, hallmark marks and QR tags

## What HUID is (so the rules in code make sense)

- Hallmarking in India is run by BIS (Bureau of Indian Standards). A hallmarked article carries three marks: the BIS logo, the purity grade (for example `22K916`), and the **HUID**.
- HUID = Hallmark Unique Identification: a **6-character alphanumeric code**, generated by BIS's system for each article and laser-marked by a recognised Assaying & Hallmarking Centre. One article, one code. A jeweller cannot make one up, and codes can be checked on the BIS Care app.
- Selling hallmarked gold jewellery without a HUID has not been permitted since 1 April 2023. Silver hallmarking is voluntary, but hallmarked silver carries a HUID. Small pieces and some goods are exempt, so the app warns by default and only blocks when the store turns on `settings.invoice.requireHuid`.
- Do not hard-code legal dates or district lists in the app; the rules change by notification. If a rule matters, link to BIS and let the store decide.

## In the data

- `inventory[].huid` and `invoice.items[].huid`: `""` or six of `A-Z0-9`. `cleanHuid()` capitalises and strips on input; `huidOk()` validates; the server enforces the pattern and uniqueness within a store (`duplicate_huid`).
- The invoice line keeps its own copy (snapshot). Picking stock goes through `applyStockToItem()`.
- Purity marks are derived: `hallmarkMark(metal, purity)` from the `HALLMARK` table in `calc.js` (22K to 22K916, 925 Sterling to 925). Add a purity to `HALLMARK` when adding one to `GK` or `PURITY`.

## QR payload (do not change casually: printed tags depend on it)

```
<app address>/#/item/<tag>?s=<storeId>&h=<HUID>&g=<gross, 3 decimals>&n=<net, 3 decimals>&p=<purity mark>
```
- Built by `tagPayload(piece)` in `routes/item.js`; read by `parseScan(text)`. Keep old parameter names readable if you add new ones (extra parameters are ignored).
- `<app address>` is `settings.store.appUrl` or the address the app is open at (`appBase()`). A `localhost` address cannot be opened by a phone; the UI warns.
- The link is a pointer. The item page shows the **live record** and compares `n`, `g`, `h`, `p` against it: a mismatch means the tag is stale and must be reprinted. Never put anything secret in the payload. The page still needs sign-in; signed-out visitors see only what the code itself carries (`scannedCardHTML()` in `auth.js`).
- `s` is checked against the signed-in store, so a tag from another store is refused.

## The encoder (`src/js/qr.js`)

Written from ISO/IEC 18004: byte mode, error correction M, versions 1 to 10 (up to 213 bytes), mask chosen by penalty score. `qrSVG()` returns a scalable SVG. Keep the payload short (about 85 bytes today, version 6). If a payload could exceed 213 bytes, shorten the app address or the parameters; `qrMatrix` throws "QR text too long".

To re-verify after any change to `qr.js`: render SVGs at sizes covering every version (lengths at each version boundary), screenshot them, and decode with an independent decoder. On macOS the Vision framework works: a ten-line Swift script using `VNDetectBarcodesRequest`. The decoded text must equal the input exactly, including multi-byte text.

## Item page, scanner, tags

- `ROUTES.item` (`#/item/<tag>`), `ROUTES.scan`, `ROUTES.tags` are in `routes/item.js`. All need Inventory view. Scanning uses the browser's `BarcodeDetector` where it exists; otherwise the type-or-paste box (which also takes a USB scanner's output) handles tags, HUIDs and full links.
- Tags print at 60 × 30 mm: QR on the left, tag, HUID, gross and net, purity mark on the right. A4 sheet is 3 across; roll is one label per page (`@page` is set when you press Print). Print CSS hides the app chrome only while `body.tag-print` is set (route `tags`).
